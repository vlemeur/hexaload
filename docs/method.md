# Methodology

## Evaluation protocol

- **Walk-forward**: 36 folds, sliding 365-day train window (8760 h), 30-day
  step (720 h), horizon h=24 (D-1), 2023-01-01 → 2026-11-24. No random split, ever.
- **2026 hold-out**: the 11 folds whose test starts ≥ 2026-01-01 are scored
  **once**, with the tuned params — never used during tuning.
- **Anti-leakage**: target-reading features (`lag_load_*`, `roll_*`,
  `lag_rte_prevision_j1`) are masked to NaN wherever `t − delay_h > as_of`
  (delay-aware as-of mask at each fold origin). Exogenous features (calendar,
  archived weather forecasts) must cover the whole test block — asserted per fold.
  Only archived weather **forecasts** enter as inputs, never observations.
- **Metrics**: point errors in MAE / RMSE / MASE (sp=24); intervals in CRPS over
  19 quantile levels (0.05–0.95), sampled.
- **Absolute reference**: RTE's published D-1 forecast `prevision_j1`.
- **RTE's forecast as an input**: `lag_rte_prevision_j1` is a public forecast, published
  ~24 h ahead — a legitimate feature, masked like any target-reading feature. Feature
  models (ridge/HGB/XGB) therefore partly learn "RTE + correction". The zero-shot
  foundation models (Timestral, Chronos) take **exogenous inputs only** (calendar +
  archived weather) and never see `prevision_j1` — their −54% vs RTE is clean.

## Metrics

Point errors: MAE = $\frac{1}{h}\sum_t |y_t-\hat y_t|$ and RMSE = $\sqrt{\frac{1}{h}\sum_t (y_t-\hat y_t)^2}$ over each 24 h test block. Scale-free error: MASE with seasonal period $m=24$, denominator on the train fold only:

$$\mathrm{MASE}=\frac{\frac{1}{h}\sum_{t}|y_t-\hat y_t|}{\frac{1}{n-m}\sum_{t=m+1}^{n}|y_t-y_{t-m}|}$$

Intervals: CRPS over 19 quantile levels $\alpha_k\in\{0.05,\dots,0.95\}$, sampled then scored empirically:

$$\mathrm{CRPS}(F,y)=\int \big(F(x)-\mathbf{1}\{x\ge y\}\big)^2 dx \;\approx\; \frac{2}{K}\sum_{k=1}^{K}\big(\mathbf{1}\{y\le q_k\}-\alpha_k\big)(y-q_k)$$

where $q_k$ is the forecast quantile of level $\alpha_k$ (K = 19).


## Tuning

Optuna **NSGA-II multi-objective (MASE, CRPS)**: 30 trials per model, 3 tuning
folds × 180 days (shorter window for cost), epoch cap for torch models, per-study
wall-clock budget. Resumable SQLite studies (`data/tuning/optuna.db`), one MLflow
run per trial (`data/mlruns/mlflow.db`, `just tune-ui`). Best point = min MASE on
the Pareto front with CRPS ≤ 1.05 × min → `results/tuning/best_params.yaml`.

## Why from-scratch deep learning is out of scope

Tuned (30 trials each, 3 folds 2024→2025): best MASE **0.32 (N-HiTS)**,
then 0.77–2.79 — vs 0.29–0.35 for GBMs and 0.27 for Timestral. **None beats RTE (0.52).**
At D-1, national hourly load is calendar + forecast weather + persistence, which the
55 leakage-safe features hand directly to GBMs; one year of one smooth series cannot
train deep nets from scratch. The dividing line is **data per parameter**: pre-trained
Timestral (209 M) wins, from-scratch nets don't. Compute budget: M4, 60 min/model,
≤20 epochs; full 36-fold torch backtest is a documented follow-up.

## Data

- RTE eco2mix national: `cons-def` (2012 → 2026-08) stitched with the real-time
  `tr` tail (~85 days); `consommation` kept as published (the ~−70 MW balancing
  residual since 2021 is documented, not "fixed").
- Weather: Open-Meteo `icon_eu` historical-forecast archive (2020-01 → 2026-11),
  never observations.
- `date`+`heure` = Europe/Paris local, `date_heure` = UTC; everything stored in UTC.
- Fetch once. The
  backtest and tuning then run fully offline from the on-disk cache; only the daily
  forecast job touches the network (RTE + live weather API), with the cache as
  fallback. `data/` and `results/` are gitignored; generated tables are never
  hand-edited.
